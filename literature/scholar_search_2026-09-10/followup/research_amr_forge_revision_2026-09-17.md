# AMR 下一轮设计：借鉴 Forge 的可操作验证反馈

日期：2026-09-17。状态：研究设计记录，尚未实现新接受器或发起新 API 请求。
本设计承接[试点诊断](research_amr_pilot_diagnosis_2026-09-17.md)，将其中“每条件最多两次修复”更新为最多四次；保留第二次修复时的结果，以观察延长修复的增量。

## 1. 借鉴什么

参考 Forge 公开论文 [arXiv:2606.22413v2](https://arxiv.org/html/2606.22413v2)，重点为 §3.1、§3.3 和 §4.7。
Forge 使用受限 Java 配置及分阶段生成；验证失败产生结构化反馈，包含问题类别、工具输出、修复指令和源代码位置，反馈重新进入生成流程，直到通过或达到生成上限。其消融还区分了编译反馈和形式验证反馈。

对本案例最有用的迁移是“固定要求 → 生成实现 → 验证 → 定位到实现的修复反馈 → 再验证”。
现阶段继续使用现有受限 JSON 控制器和 AMR 仿真，以便识别本轮失败因素。
把 Java、多个证明后端和分阶段生成同时引入，会使新旧结果难以归因；这些不作为本轮变量。
后续若研究问题转向工业实现的模型提取，再单独设计受限通用语言前端与提取验证。

**归属边界：**“期望行为、规则位置与修复指令”的反馈设计借鉴 Forge；下文的累计反例和循环停止策略，是针对本项目观察到的往返修补提出的扩展，不声称来自该论文。本文依据公开论文，未复现其工具链。Forge 的流水线迭代与本项目单次 API 修复调用不具有直接可比的轮次含义。

## 2. 放宽表达和修复空间

| 项目 | 已完成试点 | 新诊断设计 |
| --- | --- | --- |
| 每函数规则数 | 8 | 12 为拟采用的常规配置；8 保留为压力对照 |
| 每条链修复上限 | 2 次 | 4 次；接受或出现程序循环时提前停止 |
| 输出 token 上限 | 2,048 | 暂保持 2,048；原输出仅 241–274 tokens，无截断证据 |
| 模型设置 | deepseek-flash、非思考、temperature=0 | 保持，避免同时改变求解设置 |
| 验收输入域 | 32 + 7 × 256 = 1,824 | 保持 |
| 安全、完成和源模型对应义务 | v1.1 | 保持 |

12 条允许自然展开约 9 类 step 分支，并留出少量余量；这是研究设计选择，不是来自工业标准的限值。
首条命中语义、动作与模式白名单、表达式长度/深度/节点数、200 KB 源码大小和 32 总分支上限均保留。
不修改已经冻结的八条解析器和旧运行证据；新解析配置应有独立 profile 标识、配置快照及校验记录。

“放宽上限”不包括允许机器人未停稳就宣告 Stopped、未清空区域就释放预约，或降低完成条件。

## 3. 反馈如何变得可操作

每次可解析候选仍检查全部 1,824 个输入。诊断器从固定规格产生以下字段：

- `stage`、`requirement_id`：失败阶段及既有义务名称；不由模型重新定义义务。
- `source_location`：当前原始候选中的函数、从零开始的规则索引/JSON 路径及条件；未覆盖时标为 `no_match`。
- `input`、`actual`、`allowed_outputs`：完整输入、实际返回、规格允许的返回集合。
- `fix_directive`：由预先写定模板生成的修复要求，描述应满足的行为及优先级，不提供参考程序或完整替换条件。
- `regression_examples`：此前出现过的输入，在本轮的输出与允许输出；既显示仍失败项，也保留已修复项。

例如，一条规则在 ObservationUsable=false、Halted=false 时返回 `(Brake, Stopped)`，应指出该规则违反停稳确认义务，该输入要求 `(Brake, BrakeRequested)`；同时明确已有停稳确认时的要求不同。其他输入字段在实际反馈中完整保留。
这直接解释错误，而不是只返回 `stop_on_invalid_or_blocked_input` 标签。

`select` 在两车均有资格时可能有多个合法动作，反馈必须列允许集合，不能把手写参考选择的某辆车强加为唯一答案。
“源码/模型均无定义”与“二者已定义但输出不同”分别标记，避免把覆盖不足误称为提取器错误。

反馈选择规则在调用前实现并冻结：

1. 当前反例最多 8 个，按函数、义务、允许输出集合和 Halted 值分组；每组按既有输入枚举顺序取首例，再按组键排序截取。避免只取 TaskActive 不同的重复例。
2. 累计池保存本链已经反馈过的具体输入。每次附最多 4 个历史例，先选重新变错的输入，再选已修复输入，再选仍未解决输入；同类按首次出现顺序选择，排除当前反例已包含的输入。
3. 历史输入的实际结果和命中位置每轮重新计算；不能沿用旧规则索引。全部反例及全域结果留在本地记录，提示中最多 12 个例子。
4. 不把完整 1,824 项真值表、手写参考源码或其他实验组的修复结果提供给模型。累计池在各条件间隔离。

该处理条件是“更丰富的结构化反馈加累计反例”整体。若它有效，本轮不能进一步判断是期望输出、定位还是历史记忆单独起作用；需要后续消融。

## 4. 最小诊断：四个条件、最多十六次新增调用

起点固定为旧协议顺序中**第一个可解析但不合格的初始候选 P2-R1**，即旧运行的 request/record 004：
[原始输出](../../../formal-artefacts/amr-deepseek-pilot/run/records/004/response.bin)。
不选某次已经改善的修复结果，不重新采样起点。它属于见过结果后的诊断材料，不是新的独立测试样本。

| 条件 ID | 每函数上限 | 反馈 |
| --- | --- | --- |
| D8-O | 8 | 原反馈：既有数量和截取规则，无累计历史 |
| D12-O | 12 | 同上 |
| D8-F | 8 | 本文结构化反馈及累计反例 |
| D12-F | 12 | 同上 |

各条件最多四次修复，合计最多 16 次新增 API 调用；复制已有起点不产生调用。
按修复轮次轮流运行四条件，条件顺序固定为表中顺序，跳过终止链。请求之间不共享聊天状态。
原任务提示只修改各条件声明的规则上限；模型、解码设置、输出额度、规格、反馈以外的修复指令保持一致。
四组都在本地计算完整诊断指标，但 O 组只能收到原反馈字段，不泄露 F 组的增强信息。

同一条链另存第二次修复时的检查点，并报告最多四次时的结果。提前终止的链明确记录停止原因，不虚构未执行的第三、四次调用。
这样既能观察前两次是否足够，也能看额外轮次是否确有收益；这不是新增独立样本数。

每轮记录：解析是否通过、首次接受轮次、源/模型义务失败输入集合、修复与新引入错误集合、对应性错误类别、规则数、token、程序摘要和停止原因。
只看总失败数会掩盖“修好 784 个、又破坏另外 784 个”的回归，因此必须保留集合差异。

**停止规则：**先完成验收；通过则停止。未通过且解析后的规范 AST 与本链任一历史候选相同，则以重复/循环停止；规则顺序保留，不做布尔逻辑等价化。无法解析时用原始字节摘要检测重复。另在达到四次修复无法预留、传输/服务失败时停止，不自动重试、不自动更换模型或追加轮次。
重复即停是一项预先固定的节约策略，不意味着数学上证明后续绝不可能成功；两种反馈条件一致应用。


## 5. 如何解释结果和继续案例

- D12-O 相比 D8-O 改善：提供规则压缩限制影响修复的线索。
- D8-F 相比 D8-O，或 D12-F 相比 D12-O 改善：提供反馈设计有效的线索。
- 只有 D12-F 成功：提示两因素可能共同限制修复，单个起点不能确证交互效应。
- 只有第三、四次成功：说明额外修复对该条件的该轨迹有帮助；不等于所有原始失败主要由轮次不足造成。
- 全部失败或循环：先检查轨迹和反馈质量；再另设模型思考模式对照，不自动消耗剩余额度。

四条件各只有一条诊断链，即使全部成功，也不能把它们当成四个独立任务，或用来估计一般接受率。
若诊断发现有效配置，下一阶段先冻结新协议，再使用事前固定的新初始调用进行评价；旧 0/6 结果始终保留。

最终案例仍应回答工业行为问题：通过检查的**原始模型输出**在相同调度下进入两 AMR 的正常通行、临时行人阻挡、观测失效和永久阻挡场景，与同接口校准控制器配对比较碰撞、预约互斥、停稳/恢复及任务完成情况。永久阻挡下安全停止和不完成应分开记录。
源码选择规则须在这些运行之前固定；不能挑选物理表现最好的输出。诊断阶段获得的通过候选最多支持探索性演示，不能并入之后独立评价的成功率。

本轮反馈改进解决“如何有效修复已知契约失败”的问题；规格是否充分表达真实安全要求、物理抽象是否正确，仍需独立场景与假设检查。增加规则数或取得全域通过不会自动补齐这些证据。
