# Independent runtime review

**Spec-compliance verdict: PASS for the declared fixed-context mechanism scope.** `Core`, `legal`, and `step` implement the state fields, typed inputs, visible events, and transition rules in `hol/interface.md`: Validate saves only a currently legal intent; Commit and Apply recheck current permission; Observe preserves saved intents; Apply clears the command; Release requires matching ownership and whole-body Clear. Advice operations do not mutate core authority state. The source controller loads the recorded selected bytes, reassesses them, checks their identity, passes current eligibility and advice facts to the source, and raises rather than substituting for a wrong source result.

The mailbox strictly parses the one-field A/B object, rejects duplicate keys, malformed/oversized values and wrong bindings, and retains the first accepted reply. In the mechanism loop a decision is latched before source selection and is not relatched while a validated proposal is pending. No-advice selection therefore reaches A through the source FIFO rule; B advice reaches B; ineligible advice cannot force a grant. E3a mutates only Commit permission rechecking, E3b only Apply permission rechecking, and E4 only waits for absent advice. Their correct/faulty contrasts produce 0/1, 0/1, and A/no-owner respectively. A fresh run exactly reproduced the recorded mechanism evidence.

**Code-quality verdict: PASS with an integration boundary that must remain explicit.** All eleven mailbox/protocol/mechanism tests pass, and all sixteen tests in the v2 suite pass. The code is small, typed at its boundaries, deterministic, and uses an independently written visible-event oracle for the constructed stale-permission failures.

The modules do not themselves implement relevant-task-change invalidation or bind a latch permanently to a proposal object. `AdviceMailbox` has no invalidation operation, and after an empty latch it may accept a later valid reply; correctness relies on the caller retaining the prior latch for an already validated proposal and discarding/recreating the mailbox when the trusted context changes. `run_mechanisms.py` satisfies the first obligation for its fixed one-context trace, while the frozen HOL interface expressly excludes mission-ID/epoch refinement. This is not a defect in the reviewed bounded witness, but it is a load-bearing requirement for the physical/API adapter and must not be claimed as implemented by these files.

Test coverage is scenario-focused rather than exhaustive transition conformance: it does not enumerate every Core state/input pair or directly test task-context replacement. That is acceptable for these Python mechanism witnesses because exhaustive core comparison belongs to the separate HOL export/conformance stage, but any deployment adapter needs explicit tests for context invalidation, decision-latch reuse, and rejection of late replies against an old context.

**Load-bearing defects in the declared bounded runtime: none. Load-bearing integration obligations: context invalidation and immutable latch-to-proposal association.**
